| 使用场景 | 结论 | 说明 |

## 2. 分项检查明细

### 2.1 代码完整性 —— 通过（3 处待补）

**事实**

- 24 个文件、4542 行 JS，无 `TODO / FIXME / XXX`，无未使用的模块。
- 全部 `.js` 通过 `node --check`；三端页面在无头浏览器中无 console 报错。
- 39 个接口、9 张表；业务状态机（active / waiting / closed）在服务端收敛，前端不做状态推断。
- 转人工、排队、分配、转接、结束五条路径都有服务端二次校验，前端按钮禁用只是体验层。

**不足**

| 问题 | 位置 | 影响 |
| --- | --- | --- |
| 启动无条件执行种子逻辑 | `server.js:9` `seedAll()` | 仅当库为空时写入，不会覆盖数据；但**误删库后重启会重建 `admin/admin123`**，等于留了后门 |
| 健康检查是静态对象 | `src/api.js:561` | 不执行任何 DB 查询，库损坏时仍返回 `ok:true` |
| 会话表无过期字段 | `src/db.js:116` | 登录一次永久有效，无法强制下线 |

### 2.2 构建与测试 —— 部分满足

**通过**

- 没有构建步骤：原生 `http` + 静态文件，`npm start` 即运行，不存在"本地能跑、线上构建失败"的风险。
- `npm run verify` 30 项断言覆盖建会话→问答→上下文→转人工→分配→接管→转接→结束→评价→统计→知识库热更新，且包含三方越权校验。

**缺口**

| 问题 | 说明 |
| --- | --- |
| 无单元测试 | `src/ai.js` 的分词与置信度、`src/stats.js` 的统计口径完全没有回归保护。改一行停用词或阈值，匹配效果会静默变化 |
| 测试依赖手工起服务 | `verify.js` 假设 `localhost:3000` 已运行，无法直接进 CI；且会写入真实数据 |
| 无 CI / 无 lint | 没有 `.github/workflows`、ESLint、Prettier，风格靠人工自律 |
| 无测试数据隔离 | 没有"临时 DB + 自动起停服务"的测试夹具 |

### 2.3 依赖与环境 —— 通过（上线需锁版本）

**通过**

- **零第三方运行时依赖**：没有 npm 供应链风险，没有 `node_modules`，`npm audit` 无对象可审。
- 攻击面极小：无模板引擎、无 ORM、无文件上传。

**缺口**

| 问题 | 位置 | 风险 |
| --- | --- | --- |
| `node:sqlite` 是实验特性 | `src/db.js` | 官方标注 API 可能变更；跨 Node 大版本升级有破坏风险 |
| `engines` 写 `>=22.5.0` | `package.json` | 过宽，等于允许任何未来版本；应锁定到具体主版本 |
| 无 `.gitignore` | 项目根 | `data/app.db` 含访客手机号、设备、城市，可能被提交进仓库 |
| 无 `.env.example` | — | 环境变量只有 `PORT`、`DB_PATH`，但新同事不知道该配什么 |
| 无容器化 / 无进程守护配置 | — | 部署形态完全靠口头约定 |

### 2.4 敏感信息与安全 —— 不满足公网要求

**通过项（实测）**

| 检查 | 结果 |
| --- | --- |
| SQL 注入 | 全部参数化；动态 `where` 只拼接固定片段，`scope=mine` 用 `Number(user.id)` 强制转数字 |
| 路径穿越 | `/../package.json`、`/%2e%2e%2fpackage.json`、`/assets/..%2f..%2fpackage.json` 均 404；`path.join` 后有 `startsWith(PUBLIC_DIR)` 二次校验 |
| 存储型 XSS | 注入 `<img src=x onerror=...>` 后，管理端 transcript 只显示文本，`window.__xss` 未置位，DOM 内无 img 节点 |
| 越权 | 访客 token 访问客服接口 401；客服 token 访问管理接口 403；原客服转接后发言 403 |
| 非法 JSON | 返回 400，不落栈 |

**未通过项（P0）**

| 问题 | 证据 | 后果 |
| --- | --- | --- |
| 口令哈希过弱 | `src/seed.js:6` 单轮 `sha256("xigu::" + password)` | 固定盐 + 无迭代，离线爆破成本极低 |
| 默认口令硬编码并打印 | `src/seed.js:175-178`、`server.js:83-85` | 任何人拿到代码即知道后台入口 |
| 登录无限流 | 实测 30 次错误全部放行 | 可被字典/撞库打穿 |
| 会话永不过期 | `sessions` 表无 `expires_at` | token 泄露后永久有效，无强制下线手段 |
| 无安全响应头 | `curl -I` 仅 4 个头 | 无 CSP / X-Frame-Options / nosniff / Referrer-Policy，缺少纵深防御 |
| token 存 localStorage | `common.js` | 一旦出现 XSS 即被窃取；当前转义可靠，但没有第二道防线 |
| 访客建档无限流 | `POST /api/visitor/session` | 单个脚本可无限写库，形成存储耗尽型 DoS |
| 无 HTTPS 方案 | 服务只监听 HTTP | 口令与聊天内容明文传输 |

> 说明：项目使用自定义头 `x-token` 而非 Cookie，跨站表单无法伪造，CSRF 风险低；但这一点目前只存在于设计里，没有写进文档。

### 2.5 性能与稳定性 —— 有明确上限

**能力边界**

| 项目 | 现状 |
| --- | --- |
| 并发模型 | 单进程、单线程、同步 SQLite；CPU 单核即天花板 |
| 水平扩展 | **不可行**：SSE 客户端在进程内存、SQLite 单写者、无共享会话 |
| 实测容量 | 约 70 条消息/秒；按 10 坐席、每人 3 路并发估算，日常负载远低于上限 |
| 存储增长 | 约 2.4KB/会话（含消息），1 万会话约 24MB |

**风险点**

| 问题 | 位置 | 说明 |
| --- | --- | --- |
| 每次刷新返回全量消息 | `src/api.js:462` `visitorState()` | 长会话（数千条）时，每条消息都触发一次全量下发 |
| 统计全量读内存 | `src/stats.js` | 把区间内所有会话与消息取出来在 JS 里算，数据量上万后看板会明显变慢 |
| 列表固定 LIMIT 无分页 | `src/api.js:984`（200 条）、`:775`（50 条） | 超过后无法翻页，也没有 `offset` 参数 |
| 2MB 请求体直接断连 | `src/api.js:36` `req.destroy()` | 客户端收到 RST 而非 413，排查困难 |
| 无优雅退出 | `server.js` | 没有 `SIGTERM` 处理，发布重启会直接掐断在途请求与全部 SSE |
| 异常不退出 | `server.js:116` | `uncaughtException` 只打印不退出，进程会"带病运行"，状态可能已损坏 |
| 无请求级超时配置 | `server.js` | 依赖 Node 默认（headers 60s / request 300s），未按业务显式设定 |
| 无背压处理 | `src/sse.js` | 慢客户端只写不检查 `write()` 返回值，极端情况下内存堆积 |

### 2.7 回滚方案 —— 缺失，且备份方式有坑

| 能力 | 现状 |
| --- | --- |
| 代码版本化 | ⚠️ 有 `package.json` 的 `1.0.0`，但无发布目录、无上一版保留、无回滚脚本 |
| 数据库迁移 | ❌ 只有 `CREATE TABLE IF NOT EXISTS`，改字段不会自动迁移，也没有 schema 版本表 |
| 备份 | ❌ 无任何备份机制 |
| 回滚演练 | ❌ 无记录 |

**实测的备份陷阱（重要）**

服务运行中执行 `cp data/app.db backup.db`，再打开备份文件对比：

```
运行中主库会话数: 94
仅复制 app.db 的会话数: 69
丢失: 25 条（27%）
```

原因：WAL 模式下新写入先在 `app.db-wal`，主库文件不是最新快照。
**正确做法**：`sqlite3 app.db ".backup out.db"` 或 `VACUUM INTO`，或停服后连同 `-wal/-shm` 一起复制。

## 3. 上线前必须修复（P0）

| 编号 | 问题 | 位置 | 修复方案 | 验收标准 |
| --- | --- | --- | --- | --- |
| **P0-1** | 弱口令哈希 + 默认账号 | `src/seed.js:6,175` | 改用 `crypto.scrypt`（或 bcrypt/argon2）；默认账号改为环境变量注入 + 首次登录强制改密；启动日志不再打印口令 | 新库不存在 `admin123`；哈希串含盐与参数 |
| **P0-2** | 会话永不过期 | `src/db.js:116` | `sessions` 增加 `expires_at`（建议 8h）、`last_seen`；校验时判断过期并滑动续期；提供"强制下线" | 过期 token 返回 401；后台可踢人 |
| **P0-3** | 登录与建档无限流 | `src/api.js` 登录/会话接口 | 按 IP + 账号双维度限流（5 次/5 分钟），失败延迟递增；访客建档按 IP 限速 | 连续 6 次错误返回 429；脚本刷建档被拒 |

| **P0-6** | 无优雅退出 / 异常不退 | `server.js:116` | `SIGTERM`：停止接入 → 通知 SSE 客户端重连 → `server.close()` → `db.close()` → 退出；`uncaughtException` 记录后 `exit(1)` | 重启无 502 尖刺；异常进程被 systemd 拉起 |
| **P0-7** | 空库自动灌演示数据 | `server.js:9` | 用 `SEED_DEMO=1` 显式开启；生产首次启动用 CLI 创建管理员 | 空库启动不产生 `agent1~3` |

| **P0-10** | 无 .gitignore / 未锁 Node 版本 | 项目根、`package.json` | 增加 `.gitignore`（`data/`、`*.db*`、`.env`）；`engines` 锁定 `22.x`；生产固定 Node 小版本 | 仓库无 DB 文件；部署脚本校验 Node 版本 |

## 4. 建议优化项（非阻塞）

### P1（上线后 1–2 个迭代内）

| 项 | 理由 |
| --- | --- |
| 消息增量拉取（`after_id`）+ 分页 | 避免长会话全量下发，直接改善访客端流量与首屏 |
| 统计预聚合（按天汇总表） | 现在每次看板都全量扫消息，数据一多就拖慢 |
| 单元测试 + CI | `ai.js` 的匹配、`stats.js` 口径需要回归保护；CI 里用临时 DB 自动起停服务跑 `verify` |
| 限流中间件（IP/访客/坐席三档） | 把 P0-3 的一次性修复沉淀成通用能力 |
| 数据保留与删除（PIPL） | 访客手机号等 PII 目前永久保留；需提供"删除我的数据"与 180 天清理策略 |
| 管理员操作审计 | 知识库增删改、强制结束、规则变更目前无独立审计流 |
| 前端错误上报 | 现在只有 toast，用户侧异常无法回流 |
| 静态资源指纹 + gzip/brotli | 便于长缓存，减少重复传输 |

### P2（架构演进）

| 项 | 说明 |
| --- | --- |
| 多实例部署 | PostgreSQL 替代 SQLite，Redis Pub/Sub 替代内存 SSE，会话与锁外置 |
| 语义检索 / 大模型 | 替换 `src/ai.js` 的 `analyze()`，保留置信度门槛与兜底转人工 |
| 工单、质检、附件、语音 | 与"会话闭环"解耦的独立能力域 |
| 多租户与组织隔离 | 对外 SaaS 的前置条件 |
| 可观测性体系 | OpenTelemetry 链路 + Prometheus 指标 + 集中日志 |

## 5. 最小上线方案（单机内网）

适用于 ≤10 坐席、≤200 并发访客、日会话 ≤1 万的内部试用。

```
Internet/内网
   │  HTTPS 443
   ▼
Nginx  ──  静态资源直出、SSE 关闭缓冲、登录接口限流、TLS 终止
   │  HTTP 127.0.0.1:3000
   ▼
Node（systemd 守护，单实例，固定 22.x 小版本）
   │
   ▼
data/app.db（SQLite WAL）  ──  每日 .backup + 保留 7 份
```

- 应用只监听 `127.0.0.1`，不直接暴露公网。
- 运行用户 `xigu`，`data/` 权限 `700`，日志归 journald。
- 备份用 `sqlite3 .backup`，禁止直接 `cp`（会丢 WAL 中的数据）。
- 具体 unit、Nginx 配置、备份脚本、发布与回滚步骤见 `docs/部署与回滚手册.md`。

## 6. 回滚方案（要点）

| 层面 | 方案 | 目标 |
| --- | --- | --- |
| 代码 | 发布到 `releases/<version>/`，`current` 软链切换；保留最近 3 个版本 | 回滚 ≤ 2 分钟 |
| 数据 | 发布前 `sqlite3 app.db ".backup backups/pre-<version>.db"`；回滚时停服还原 | RPO 取决于备份频率（建议每小时） |
| Schema | 迁移脚本按序号存放，回滚脚本成对提供；禁止只改 `CREATE TABLE IF NOT EXISTS` | 可逆 |
| 配置 | `settings` 表变更前导出 JSON 快照 | 可回退阈值与规则 |
| 演练 | 每次发布前在预发执行一次"删库→恢复→切版本" | RTO < 10 分钟 |

**禁止动作**：在生产库上直接 `DELETE` 或 `VACUUM`；用 `cp` 覆盖正在运行的主库；回滚时只回代码不回数据。

## 7. 最终结论

1. **功能层面可以交付。** 三角色权限边界清晰，人机协同闭环完整，30 项端到端断言全通过，界面在桌面与移动端均可用。
2. **工程层面还差一层"运维壳"。** 目前缺的不是功能，而是身份安全、输入校验、日志监控、备份回滚这四类"出问题时才想起"的能力。
3. **定位建议**：作为**演示/答辩/作品集**可以直接上线；作为**内网试用**需先关闭 P0-1 至 P0-10；作为**公网生产**不建议在当前架构上硬撑。
4. **投入产出**：3–5 人日补齐 P0，即可支撑单机内网场景；若要公网多租户，则是一次架构重构，不是补丁能解决的。

> 本报告中的全部数据均由实测得出，复现命令见各章节；压测与安全探测均在独立实例（`PORT=3100`、独立 DB）上执行，未污染演示数据。
